# 開発元への報告（設計メモ）

目的：利用者がフローを作っている途中で、AI が SpellSheet の不具合や足りないノードに気づいたら、それを開発元に届ける。使う人の実際の業務で何が足りないかは、開発元がいちばん知りたいことなので、気づいた AI が下書きまで書き、利用者が中身を確かめて送る。

## 流れ

```
AI（MCP） ── report_to_developers ──▶ 下書き（この PC の reports/）
                                         │  窓の帯に「開発元への報告 n」
                                         ▼
                                  Writer の「開発元への報告」ダイアログ
                                  件名・本文を直す → 送る／送らない／あとで決める
                                         │ 送る
                                         ▼
                        中継サーバー（Cloudflare Workers、services/report-relay）
                        回数の制限・同じ件名はまとめる・@ や # を無害にする
                                         │ GitHub の鍵はここにだけある
                                         ▼
                           GitHub の issue（spellsheet/spellsheet、ラベル from-app）
```

1. AI は `report_to_developers` に種類（`bug`：SpellSheet の不具合、`missingNode`：フローに要るのにないノード）、件名、本文、ノードの種類を渡す。書くのは下書きだけで、すぐ返る。AI は待たず、送るよう利用者に頼まない（作業を続け、回避できるなら回避する）。
2. 下書きは作業場所のこの PC の側（`FileStore::local_root` の `reports/`）に 1 件 1 ファイルで残る。同じ種類・同じ件名の下書きがあれば置き換え、待っている下書きは 10 件まで。
3. Writer は `reports/` を見張り、下書きがあれば窓の帯に「開発元への報告 n」の札を出す。人を待たせているものではないので、灰色の控えめな札にし、ダイアログを勝手に開いたり Windows の通知を出したりはしない。AI チャットの返事でも「報告を残した」と一言伝える。
4. 札を押すとダイアログが開く。件名と本文はその場で直せる。押せるのは「あとで決める」「送らない」「GitHub で書く」「送る」。
5. 「送る」で、利用者が直した件名・本文と、ノードの種類・版・OS の種類だけを中継サーバーへ送る。中継サーバーが issue を作り、その場所を返す。送ったものは 30 日のあいだ一覧に残る（issue の場所を開ける）。

## 同意と既定

- **既定は送らない。** 利用者が「送る」を押さない限り、どこにも送られない。閉じる（Esc・外側を押す・「あとで決める」）と下書きは残り、打ち直した文も Writer を閉じるまで残る。「送らない」は下書きを消す。
- ダイアログを開いたときの入力の場所は本文の欄にする。Enter の押し間違いで送ったり消したりしないため。
- ダイアログの冒頭で「送ると GitHub で公開され、誰でも読める。送らなければ、どこにも送られない」と言い、送るもの・送らないもの（フロー・ファイル・画面の画像は送らない）を書く。
- 送っている間はどのボタンも押せず、Esc でも閉じない。失敗したら理由を出し、下書きと打った文はそのまま残る。

## 業務の内容と個人情報

- AI への指示（ツールの説明と MCP の instructions）で、業務のデータ・ファイルの中身・人や会社や取引先や社内システムの名前・URL・パス・画面の画像を書かないよう、一般的な言い方（「Excel の表を読み、Web のフォームに 1 行ずつ入力する」）で書くよう求める。
- それでも書かれたときのために、Core の `report::redact` が、下書きを受け取ったときと利用者が直したときの両方で、メールアドレス・電話番号・URL（SpellSheet 自身のページは残す）・共有フォルダー・パスの中の Windows のユーザー名を `[メールアドレス]` などに置き換える。伏せた数はダイアログに出す。
- 機械で伏せられるのはここまでで、業務や社名は見分けられない。だから最後は利用者が読んで消す。ダイアログの注意書きがそれを頼む。

## 中継サーバー

GitHub の鍵をアプリに入れると、配った実行ファイルから誰でも取り出せ、issue を荒らされたり、鍵の権限によってはリポジトリを書き換えられたりする。そこで鍵は中継サーバー（Cloudflare Workers）の秘密の設定にだけ置き、アプリは中継サーバーの住所しか知らない。

中継サーバーは誰からでも呼べるので、次のように守る（`services/report-relay/src/worker.js`）。

| 守り | 中身 |
| --- | --- |
| できることを絞る | issue を作ることと、コメントを足すことだけ。ラベルは `from-app` と `bug` / `node-request` に決め打ち。鍵はこのリポジトリだけ・Issues の読み書きだけの fine-grained token |
| 形を確かめる | JSON だけ、32 KB まで、件名 120 字・本文 6,000 字まで、種類・ノードの種類・版の形を確かめる |
| 回数を絞る | 送り元の住所（ハッシュにして保存）ごとに 1 時間 5 件・1 日 20 件、全体で 1 日 200 件 |
| まとめる | 同じ種類・同じ件名（空白と大文字小文字を除く）が 90 日以内にあれば、新しい issue を作らず先の issue にコメントで足す（1 件の issue に 20 件まで） |
| 無害にする | 本文の `@名前` と `#番号` の間に見えない文字を入れ、誰にも通知が飛ばず、ほかの issue にもつながらないようにする |

送り先の住所は、作るときに環境変数 `SPELLSHEET_REPORT_URL`（リリースではリポジトリの変数 `vars.SPELLSHEET_REPORT_URL`）で決める。住所のない版では「送る」を出さず、「GitHub で書く」（GitHub の新しい issue の画面を、利用者が直した件名と本文を入れて開く）だけになる。自分の GitHub アカウントで送る道なので、中継サーバーが止まっていても使える。

## 置き場所

| もの | 場所 |
| --- | --- |
| 下書きと送った記録 | `spellsheet_core::report`（`ReportStore`、`redact`） |
| AI の道具 | `crates/spellsheet-mcp/src/server/report_tools.rs`（許可クラスは write） |
| 送る・消す・開く | `apps/studio/src-tauri/src/reports.rs` |
| 画面 | `apps/studio/src/components/ReportDialog.tsx`（札とダイアログ）、`lib/reports.ts` |
| 中継サーバー | `services/report-relay/`（デプロイの手順は README） |

## 今はしないこと

- 送った報告の一覧の画面（今は送った直後に issue を開けるだけ）。
- 設定で報告そのものを止めること。下書きは送られないので、困ったら「送らない」で足りる。要望が出たら設定の「AI」の節に足す。
- 実行ログや画面の画像を添えること。業務の内容が混ざりやすいので、入れるなら利用者が一つずつ選ぶ形にする。
